## 1. 전체 흐름

사진 한 장이 지나가는 길과, 각 단계의 주인이다.

```
640px 컬러 사진
 └ 띠 ROI 자르기 (위·아래 비율)                         … 지금 그대로
    ├ 노면 마스크 road  (컬러 → 0/255)                   … A  io_utils.road_mask       [새로]
    └ 흑백 → 전처리 (상태에 맞는 것만)                    … A  analyze·preprocess       [보완]
         └ 어두운 영역 후보를 한 번에 뽑기                 … B  detect.extract_dark_regions [새로]
              └ 형태로 균열 / 포트홀 나누기                … B  detect_cracks·detect_potholes [새로]
                   └ 노면 밖 후보 지우기                  … C  pipeline (USE_ROAD_MASK)  [기반에서 끝남]
                        └ 정답과 비교·표·그림              … C  evaluate·evaluate_train·run_experiment
```

- **띠 ROI**: 사진에서 위·아래 비율로 잘라 낸 가로 띠. ROI(Region Of Interest)는 '관심 영역'이라는 뜻이다.
- **노면 마스크**: 띠 안에서 '여기가 도로 면이다'를 255, 아니면 0으로 칠한 흑백 영상. 건물·차·풀숲에서 나온 오검출을 지우는 데 쓴다.
- **후보**: 균열이나 포트홀일지도 모르는 영역. 넓이·모양 값이 든 dict로 주고받는다(CONTRIBUTING 2장).
- 지금은 1차 방식(`DETECT_MODE = "legacy"`: Canny 에지로 균열, DoG로 포트홀)이 돌고 있다. B가 새 방식(`"dark"`)을 만들고, 실험에서 더 나으면 바꾼다.
- 특징점(Harris·SIFT)과 매칭은 손상 검출에는 쓰지 않고, 전처리 전·후를 비교하는 지표로 보고서에 남긴다(지금 코드 그대로).

**기반(c-foundation)에서 이미 해 둔 것** — 아무것도 바뀌지 않게(동작 보존) 자리만 만들었다.

| 자리 | 지금 하는 일 | 채울 사람 |
|---|---|---|
| `io_utils.road_mask` | 띠 전체를 노면(전부 255)으로 돌려줌 | A |
| quality의 `blur_ratio` | NaN | A (Must, v1 바로 뒤) |
| `detect_*(gray, road=None)`, `DETECT_MODE` | legacy는 그대로, dark는 '아직 구현 안 함' 오류 | B |
| `extract_dark_regions` | '아직 구현 안 함' 오류. docstring에 단계가 다 적혀 있음 | B |
| 후보의 새 키 | thickness·dt_width·circ_inv는 계산됨, contrast·score는 NaN | B (dark에서) |
| `pipeline` 노면 마스크 | `USE_ROAD_MASK = False`면 1차와 같음. 켜면 노면 밖 후보를 지움 | C (켤지 결정) |
| `visualize.draw_road` | 칠하지 않은 복사본을 돌려줌 | C (Must: 최종 시연에서 노면 마스크를 보여 줌) |
| config 새 값 | 각 구역 맨 아래에 Plan.md 출발값 | 각 구역 주인이 확정 |
| 새 도구 | `tools/show_road_mask.py`, `tools/shape_scatter.py` 뼈대 | A |
| 새 시험 | 각 시험 파일에 @todo로 건너뛰는 시험 | 각자 |

기반을 넣기 전과 뒤의 결과가 같은지 C가 확인했다: 39장의 row·후보 수, 학습 804장 평가 요약(후보 6,588개, 찾은 정답 67개, 정답률 10.4%)이 모두 같다. 대신 후보 새 키(형태 값)를 계산하느라 검출 시간이 영상당 약 3~5ms(15~23%) 늘었고, 팀이 이를 받아들였다. 보고서에는 최종 실행 값만 쓰고 검출 시간에 형태 값 계산이 들어 있다고 적는다.

## 4. 정답 박스 표시 (WP6, 전원)

정답 박스(GT, Ground Truth)는 '여기에 균열·포트홀이 있다'고 사람이 그린 상자다. 39장 모두 정답이 있어야 39장의 성능을 자동으로 잴 수 있다.

**도구**: `python tools/label_gt.py` → 사진 목록에 정답 상태(GT n개 / GT 없음)가 나온다 → 번호 입력 → 터미널에서 `c`(균열)·`p`(포트홀) → 창에서 마우스로 상자 → Enter → 다 그렸으면 터미널에서 `q`(저장 후 끝).

**기준** (B가 10/10 09:00에 공지한다. RDD2022 학습 데이터와 같게 — Plan.md 3.8)

- 균열: 이어진 균열 한 줄기마다 그 줄기를 감싸는 상자 하나. 갈래가 크게 나뉘면 따로 그린다.
- 포트홀: 움푹 패인 곳의 테두리를 감싸는 상자.
- 손상 없는 사진: 상자를 그리지 않고 바로 `q`. 머리글만 있는 CSV가 생기고, 이것이 있어야 '손상 없음'으로 평가에 들어간다(파일이 없으면 평가에서 빠짐).
- 같은 장소를 여러 조건으로 찍은 사진(own_09·10·11·19 등)은 같은 손상을 같은 기준으로 그린다.
- 이름에 none이 있어도 손상이 보이면 그린다. 이름과 다르면 단톡방에 알린다.

**교차 검수** (10/10 22:00까지): A는 B가 표시한 것, B는 C가 표시한 것, C는 A가 표시한 것을 본다. `label_gt`로 사진을 열고 `c`를 누르면 창에 기존 상자가 보인다. 보고 나서 창에서 `c`(선택 취소) → 터미널에서 `q`. 고칠 곳은 표시한 사람에게 알리고, 판정이 엇갈리면 B가 정한다.

**커밋**: 자기가 표시한 `gt/<사진 이름>.csv`만 골라 `[A] 정답 박스 12장`처럼 커밋한다. gt/는 B 폴더지만 표시는 나눠 하므로 자기 몫은 각자 커밋한다(사진마다 파일이 따로라 충돌이 없다).

## 5. 공통 규칙 (CLAUDE.md·CONTRIBUTING.md 요약)

- **자기 파일만 고친다.** 파일 주인은 CONTRIBUTING 1장. 남의 파일을 고쳐야 할 것 같으면 고치지 말고 주인에게 말한다.
- **함수 약속(이름·입력·출력)을 바꾸지 않는다.** CONTRIBUTING 2장 표. 바꿔야 하면 단톡방에서 7장 절차.
- **숫자는 config 자기 구역 맨 아래에** 둔다. 주석에 단위와 근거. 구역 사이 빈 줄·주석 줄은 지우지 않는다. 바꾸면 `docs/part_X.md` 표에 한 줄.
- **영상 이름으로 나누는 예외 처리 금지.** 값은 모든 영상에 하나다.
- **src/ 안에서는 print·cv.imshow·파일 저장 금지.** 확인 출력과 그림 저장은 tools/와 tests/에서.
- **@todo 시험**: 시험 파일의 `@todo(...)`가 붙은 시험은 구현 전이라 건너뛴다. 자기 기능을 구현하면 그 줄(`@todo(...)`)을 지우고 통과시킨다. **기대값을 고쳐서 통과시키지 않는다.** 기대값이 이상하면 단톡방에 알린다. 이유에 'Should'가 적힌 시험은 실패하면 @todo로 두고 한계로 보고한다.
- **학습과제 먼저** (확정본 6장): 각 단계를 구현하기 전에 맡은 학습과제(확정본 4.2)를 먼저 공부하고 단톡방에 3~5줄로 공유한다. A는 1·5번, B는 2·3·4번, C는 6번. 특징점·매칭은 학습과제가 아니다(수업에서 다룸, 전처리 전·후 비교 지표로만 씀).
- **시작 전에** GitHub Desktop에서 Branch → Update from main. **끝내기 전에** `check_contract`와 자기 시험을 돌린다.
- **커밋**: Changes 목록은 처음에 전부 체크되어 있다(= `git add .`). 자기 파일만 체크한다. 메시지는 `[A]`·`[B]`·`[C]`로 시작한다. config.py를 체크했다면 오른쪽 diff에서 자기 구역만 바뀌었는지 본다.
- **AI 도구를 쓰면** `docs/ai_log_X.md` 표에 한 줄: 날짜, 도구, 프롬프트 요약, 받은 결과를 어떻게 고쳤나, 디버깅 과정.
- **Push와 PR은 본인이** 한다(Push origin → Branch 메뉴 → Create pull request, base는 main). 병합은 Create a merge commit.
- **results/와 사진은 Git에 올리지 않는다**(.gitignore). 그림은 단톡방이나 드라이브로 나눈다.

| 특이도 | 손상이 없는 사진 중 (노면 안) 후보가 0개인 사진의 비율 |
| 정밀도 / 재현율 | 후보 중 맞은 후보의 비율 / 정답 중 찾은 정답의 비율 |
| 균형 정확도 | (민감도 + 특이도) ÷ 2. 아무것도 검출하지 않으면 50% |
| 기준선 | '아무것도 검출하지 않는 방법'의 점수. 이것보다 나아야 의미가 있다 |
| 영상당 오검출 | 사진 한 장에 맞지 않은 후보가 평균 몇 개인가 |
| 영상 단위 정답률 | 맞힌 사진 ÷ 전체 사진. 항상 기준선(검출 없음의 정답률)과 같이 적는다. 39장 도전 목표 60%가 이 값이다 |
| 우연 대조군 | 다른 사진의 정답과 비교했을 때 우연히 맞는 비율. 실제 − 대조군 = 우연을 뺀 재현율 |
